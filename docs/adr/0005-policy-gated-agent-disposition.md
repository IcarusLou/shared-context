# Gate automatic Candidate disposition behind a server-enforced policy

Candidates are dispositioned in three tiers after every accepted Checkpoint. The session Agent may discard process-level conclusions and exact duplicates of still-accepted Contexts, and may confirm a Candidate automatically, but an automatic confirmation is accepted only when the server itself verifies the permission surface: the Review is still pending, its `candidate_status` is `ReadyForReview`, the top assessment relation is `novel` or `supports`, the request carries no `edits`, and the primary Space is an existing Space or a server-produced recommendation. ("The Review is `ReadyForReview`" was ambiguous between two distinct fields and read as the one the listing published: `ready_for_review` on a compact row is a *triage-visibility* flag that is deliberately true for `NeedsSpaceReview`, `ExactDuplicateReview` and `PotentialContradictionReview` as well. The clause the server enforces is `candidate_status`; the listing publishes `auto_confirmable`, derived from the same predicates, so the two faces of one state cannot disagree.) Contradictions, revisions, exact-duplicate supersede decisions, new-Space governance beyond server recommendations, and anything the Agent is unsure about always escalate to a human. A violation is rejected as `auto_confirm_not_permitted`, never silently downgraded. `candidate_confirm` remains the only boundary that produces accepted knowledge; ADR-0003's "explicit human confirmation" is amended to "explicit disposition — by a human, or by the session Agent inside this server-verified surface". Discard remains a local runtime decision and writes no Git fact.

Every confirmation and discard records `decision_source` (`human`, the default, or `agent_policy`), and every confirmation records `author` — the username portion of the global `git config user.email`, cached in the install manifest (the knowledge repository's local Git identity is a fixed writer identity and is not an author source). Both live only in event `annotations`, the one open extension boundary; they never enter the event payload, the confirmation operation hash, or any replay identity. Automatically accepted Contexts are revocable in batch by originating session, and the human reversal rate of automatic confirmations is the only input for widening or narrowing the permission surface.

Two repository rules are formalized. First, the knowledge repository is append-only at the file level: every write adds new files under the managed roots and never modifies or deletes an existing path — this codifies the invariant the writer already enforces. Domain state still evolves by appending events (an intent revision without the provisional flag promotes a Space; a `context.space_association_changed` event with the `correction` origin re-homes a Context), so append-only constrains history, not governance. Second, schema evolution is versioned: an authoritative change — any new event type or payload field — requires a new `schema_version` and a new bundled schema file, degrading on older installations via the unknown-schema quarantine; `schemas/event-v1.schema.json` is byte-frozen; `annotations` (including `producer` and `origin_hint`) remain the only place a field may be added without a version bump.

## Considered options

- Allowing files created on the installation work branch and not yet merged into the default branch to be modified in place was rejected. It would invalidate the exactly-one-addition assumption behind `introducing_commit_oid` and its per-path cache, orphan the runtime tables that reference Git events by random UUID, require rewriting `validate_append_only_since` around a merge-base with a PR-merge race, and — without history rewriting, which the non-force push model forbids — store more bytes than pure appending, not fewer.
- Recording `decision_source` as a payload field of `candidate.confirmed`, or adding a `candidate.discarded` event type, under `schema_version: "1"` was rejected: `deny_unknown_fields` and the closed event-type set make either change a hard parse error on older installations, which turns their `knowledge sync` into a permanent fail-and-rollback loop while the writing installation notices nothing.
- Deferring Candidate submission facts to confirmation time, so discarded Candidates never reach the shared repository, was evaluated and explicitly not adopted (2026-09-04 decision); discarded Candidates continue to leave their submission events in the repository.
- A separate provisional-acceptance lifecycle (observation period before full acceptance) was rejected as a second state machine; provenance annotations plus batch revocation cover the same need.
