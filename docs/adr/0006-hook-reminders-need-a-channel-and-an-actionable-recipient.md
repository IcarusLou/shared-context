# Send a Hook reminder only where the host accepts it and only when its recipient can act

A Hook reminder is worth its bytes only when the host will deliver it and the Agent receiving it can do something about it. Two reminders failed one of those tests each in real sessions, and both are corrected here.

**The channel.** Codex deserializes a Hook's `hookSpecificOutput` as an internally tagged enum, and in 0.153.4 that enum has exactly six variants: `PreToolUse`, `PostToolUse`, `PermissionRequest`, `SessionStart`, `SubagentStart`, `UserPromptSubmit`. `Stop`, `PreCompact`, and `SessionEnd` have no variant, so emitting the block on one of them is not a dropped field but a rejected object: the whole output fails to deserialize and the `systemMessage` beside it dies with it. Session 01a08017 showed the consequence — `hook returned invalid stop hook JSON output` on every turn, the TurnStop checkpoint request never delivered, and the same silent failure on every `PreCompact`. `encode_hook_output` therefore emits `hookSpecificOutput` on exactly the three canonical events Codex has a variant for (`SessionStart`, `PostToolUse`, `PromptSubmit`) and encodes the other three as `systemMessage` alone, which those events' base output shape does accept. The `PreCompact` join that merged the boundary line with a re-stated activation marker is removed with it: a compacted Codex session gets its marker from the `SessionStart` with `source: "compact"` that Codex re-sends after compaction, which the decoder already accepts and which renders the marker unconditionally. This is a Codex encoding-layer constraint only; Cursor carries both fields on every lifecycle event and is unchanged. One Runtime decision does depend on it, though, and is corrected in the same change: the Hook spends a Session's one-shot self-healed activation marker only on an event the *host in front of it* will actually deliver, so that question is asked of the adapter that owns the wire — `delivers_model_visible_context`, derived in Codex's case from the same whitelist above — rather than restated as a Runtime constant that was right for one host and wrong for the other. The Runtime keeps one policy of its own on top of the wire answer: a Prompt is never the event that states the marker.

**The recipient.** The `SessionStart` maintenance hint — one line naming the count of pending Candidate Reviews and the `candidate_list` tool — is removed. It named work the receiving Agent structurally cannot do: `candidate_list` is scoped to the calling Session, so the five pending Reviews session 01a08017 was told about belonged to other sessions and were invisible to it. What the hint reliably produced instead was an empty `claims: []` checkpoint, because "call `candidate_list` after your first checkpoint" reads as an instruction to checkpoint. The count itself stays: `sctx maintain run` still records it in `state/maintain-digest.json`, and `sctx maintain status` and `sctx doctor` still report it to the person who can act on it. Only the injection is gone, and with it the second consumer of the single `additional_context` slot.

## Considered options

- Reaching the model on a Codex `Stop` through `decision: "block"` with a `reason` — the one field there whose text the Agent sees — was rejected. Blocking a completed turn to make the Agent read a reminder is a control decision, and the adapter returns no decision, continuation, or updated input on any event; a checkpoint request is not worth becoming the first exception. The request stays a user-visible `systemMessage`, and the Agent-facing path to a checkpoint remains the Skill and the activation marker.
- Keeping the `PreCompact` model-visible reminder by moving it to the `SessionStart` Codex sends after compacting was considered and found to be already true: that `SessionStart` renders the marker unconditionally, so `PreCompact` losing `additionalContext` costs nothing against the behavior that shipped, where the entire output was rejected and neither field arrived.
- Keeping the model-visibility question as one Runtime constant covering both hosts, now narrowed to the events both agree on, was rejected. It was already that, and being right for both hosts at once is exactly what it could not be: a Cursor `preCompact` and `stop` carry `user_message`, and narrowing to the intersection would take a real Cursor delivery away to describe a Codex limitation.
- Offering the unspent delivery again on a later event, so a Codex lease repaired at a boundary event still gets its marker, was scoped out and recorded as deferred-issues #37. It requires a `SessionStart` to start recording the delivery it makes, which is a lease-record change, and doing it here would have mixed a store-semantics change into an encoding fix.
- Version-gating the whitelist on the reported Codex version was rejected for the same reason host versions are never gated anywhere else in this adapter: the reported version is an informational label, and a narrower output is correct on every version, including ones that later add the missing variants.
- Rewording the maintenance hint to say "do not checkpoint for this" was rejected. It would keep paying context bytes for a count the Agent still cannot act on, and the empty checkpoint was the symptom, not the defect.
- Widening `candidate_list` to installation scope so the hint would have been actionable was rejected as the wrong direction: Candidate disposition is a human governance boundary (ADR-0005), and an Agent asked to triage another session's Reviews has none of that session's Working Intent.
